# Aegis

> 面向 Codex 的 AI 原生软件工程治理与项目认知基础设施。

Aegis 是面向 OpenAI Codex 编码智能体的软件工程治理系统。它规定一项工程结论需要什么证据、由谁审查、在什么条件下可以被接受，并保存这些判断的依据，供后续开发复核。

Aegis 使用“AI 原生软件工程”描述 AI 参与需求理解、方案设计、代码实现、验证和交付的生产方式。工程师在这些工作中需要反复确认需求边界、检查证据、处理分歧。Aegis 将其中可以明确规定的要求交给系统执行，人类保留目标选择、重大取舍和最终接受的责任。

## 为什么需要 Aegis

成熟的软件工程会通过不同职责建立制衡：提出需求的人、设计系统的人、实现代码的人、验证结果的人和批准交付的人，通常不会拥有完全相同的视角与利益。

同一个 Codex 上下文可能连续解释目标、选择方案、编写代码，再设计验证并宣布工作完成。

当实现和验证沿用同一个错误前提时，测试可以通过，结果却仍然偏离需求。同一上下文还可能把自己的解释当成证据，遗漏本应由独立审查发现的问题。

Aegis 针对这种结构性风险提供四项治理能力：

1. 过程约束：每个工程阶段有明确的进入条件、完成条件和责任边界。
2. 独立判断：关键结论由承担独立审查职责的智能体复核。
3. 证据要求：工程状态的推进需要可检查的事实支持。
4. 认知延续：项目同时保存结果、成立理由、适用边界和失效条件。

## 核心理念

### 1. 治理对象是软件生产过程

Aegis 从需求和约束进入项目时开始治理，直到工程结论经过审查并被接受。实现、验证和异常处置都要遵守已经确认的边界。

### 2. 职责分工包含解释权分离

Aegis 为每项职责定义可见事实、判断范围、变更权限和复核关系。关键审核由真实创建的独立智能体承担，分别保留身份、上下文和输出记录。

Aegis 使用“解释权分离”描述不同职责解释和批准事实时的权限边界。审核工作的评价依据是审查是否完整、结论是否有证据；审核者可以保留拒绝结论及其理由。

### 3. 证据高于自我声明

“已经完成”“测试通过”“风险可接受”属于工程主张。Aegis 要求重要工程主张由相匹配的证据支持，并让证据接受独立判断。

口头确认或一段完成说明不足以单独推动工程状态。

### 4. 异常时停止推进

异常发生时，Aegis 停止受影响的流程并保留失败记录。缺少证明的条件按未满足处理，后续工作需要重新验证相关条件。恢复过程保留原有失败结论和证据。

### 5. 项目需要拥有自己的认知

Aegis 将设计动机、约束、取舍、反例、证据和失效条件作为项目资产保存。后续工程活动可以继承已有判断基础，并依据当前条件检查历史结论的有效性。

### 6. 速度服从质量阈值

Aegis 在满足事实、范围和证据要求后优化执行速度。缩短流程、减少调用或复用历史结果，都需要保留必要的审查和验证。

## 架构抽象模型

以下模型描述 Aegis 的设计职责，由五个治理层和外部责任主体组成。各层的实现与验证进度见“当前进度”。

```text
┌──────────────────────────────────────────────┐
│ 人类 / 组织 / 合同 / 法律：授权、边界与最终责任 │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│ 模型行为治理：识别失败模式并调整治理强度       │
├──────────────────────────────────────────────┤
│ 工程生命周期治理：约束工作如何进入、推进与结束 │
├──────────────────────────────────────────────┤
│ 职责与解释权分离：限制谁可以对什么作出判断     │
├──────────────────────────────────────────────┤
│ 项目语义空间：保存理由、约束、证据与失效条件   │
├──────────────────────────────────────────────┤
│ 运行时治理：把规则转化为可执行、可拒绝的边界   │
└──────────────────────────────────────────────┘
```

### 模型行为治理

模型行为治理关注 Codex 在工程活动中反复出现的失败模式。该层的设计目标是根据已观察到的问题，调整审查要求、证据要求和运行限制。

### 工程生命周期治理

工程生命周期治理规定每个阶段需要哪些输入，以及什么条件下可以进入下一阶段或结束。每次状态变化都需要相应的工程事实支持；已经确认的边界需要经过重新审查才能变更。

### 职责与解释权分离

这一层分别约束谁可以产出事实、解释证据和批准结论。提出方案与接受结果的职责相互制约，减少同一主体为自己的成果作出全部判断的情况。

### 项目语义空间

项目语义空间保存工程判断及其联系。需求、设计和验证结果都有可追查的来源；后续工作可以检查某项决定依赖哪些前提，以及这些前提是否仍然成立。

### 运行时治理

运行时治理层负责执行准入、拒绝和恢复规则。该层需要在正常执行和异常情况下维持相同的约束，其有效性需要分别验证。

### 外部责任主体

产品负责人、技术负责人、组织授权体系、合同和法律共同构成 Aegis 的外部责任环境。Aegis 保存判断链与证据链；有权作出决定的人类和组织承担最终责任。

## 项目认知与推理库

推理库是 Aegis 保存项目长期认知的持久化载体。推理库保存项目可以继续依赖的判断结构，包括：

- 为什么采用当前方向；
- 哪些约束决定了这个方向；
- 哪些替代方案曾被否决；
- 什么证据支持当前结论；
- 出现什么变化后必须重新审查。

推理库用于回答工程决策“为什么成立”。当需求、环境或实现发生变化时，历史判断需要按其适用条件重新检查。Aegis 使用“项目认知”表示项目持久保存并持续校验这些判断依据的能力。

这使维护者可以从项目保存的材料重建决策背景，减少对某个开发者或某段聊天记录的依赖。认知材料与具体执行的运行记录分别管理，各自承担长期知识和过程证据的职责。

## 人在 Aegis 中的位置

Aegis 将人类工程师的注意力集中到以下位置：

- 在前端聚焦目标、范围、约束和重大架构取舍；
- 在过程中处理真正需要责任判断的例外与冲突；
- 在末端检查关键证据并作出最终接受决定。

需求、证据和状态的日常检查由系统执行。超出既定授权的取舍交由人类处理。

## 系统范围

Aegis 当前的实现与验证范围如下：

- 智能体：OpenAI Codex；
- 使用者：单一受信任开发者；
- 运行环境：开发者控制的 Windows 本地环境；
- 治理对象：由 Codex 参与的需求理解、方案设计、代码实现、验证和交付活动。

企业身份与权限体系、多人协作治理、其他操作系统和其他模型生态不在当前验收范围内。

## 当前进度

进度依据：2026-09-06 的验证记录。

Aegis 当前处于 V3 机制化建设阶段，尚未达到生产就绪。核心实现已经可以运行，真实多智能体流程已在受控环境中完成；当前环境的整体验收仍未结束。

### 版本演进

#### V1：原则探索

V1 建立由工程状态与证据驱动 AI 编程活动的初步方法，并形成职责分离、边界冻结和失败关闭原则。

#### V2：工程实践

V2 将治理原则用于长期软件工程任务，围绕边界漂移、缺少证据的完成声明和上下文丢失开展实践。

这些实践提出了进一步的要求：流程约定需要稳定的执行机制，项目判断需要在会话结束后仍可检查。

#### V3：机制化建设

V3 将上述原则落实为持久化的项目认知、独立审核和运行时约束，并验证这些机制在正常执行与异常情况下的行为。

## 项目定位

Aegis 是面向 AI 生产参与者的软件工程治理基础设施：

> 当 AI 成为主要生产参与者时，项目仍然拥有自己的边界、记忆、证据、判断秩序和最终责任。
