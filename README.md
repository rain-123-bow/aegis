# Aegis

> 面向 Codex 的 AI 原生软件工程治理与项目认知基础设施。

Aegis 关注的不是“怎样让 AI 写出更多代码”，而是一个更根本的问题：当 AI 深度参与需求理解、方案设计、实现、验证和交付时，如何保证整个软件生产过程仍然可审查、可追溯、可复现，并由人类承担最终责任。

它把 AI 编程从一次对话或一次代码生成，提升为一套受约束的工程活动。Aegis 的目标，是将过去依赖资深工程师个人经验维持的边界意识、审查习惯、证据要求和责任判断，转化为项目可以持续执行和继承的治理能力。

## 一句话理解

**Aegis 不是替 Codex 思考，而是治理 Codex 参与软件生产时，哪些结论可以成立、由谁判断、需要什么证据，以及这些判断如何成为项目的长期认知。**

## 为什么需要 Aegis

成熟的软件工程会通过不同职责建立制衡：提出需求的人、设计系统的人、实现代码的人、验证结果的人和批准交付的人，通常不会拥有完全相同的视角与利益。

当这些工作被集中到同一个 AI 上下文中时，角色名称仍然可以存在，但真正的独立性可能已经消失。一个模型可能同时：

- 解释目标；
- 选择方案；
- 编写实现；
- 设计验证；
- 解释验证结果；
- 宣布工作完成。

这会形成一种危险但不易察觉的失败：局部推理彼此一致，过程看起来完整，最终结论却可能从一开始就建立在错误前提上。问题不一定是模型能力不足，而是同一认知主体控制了事实链、解释权和最终判断权。

Aegis 从这一风险出发，试图解决四类工程问题：

1. **过程可信**：工作不能因为“看起来完成”就被视为完成。
2. **判断独立**：关键结论不能只由结论的生产者自己证明。
3. **证据闭合**：工程状态必须由可检查的事实推动，而不是由语言承诺推动。
4. **认知延续**：项目不仅要保存结果，还要保存结果为什么成立、何时失效。

## 核心理念

### 1. 治理对象是软件生产过程

Aegis 不把代码生成视为孤立能力。它治理的是从意图进入项目，到工程结论被接受的完整过程，包括边界形成、判断分离、执行约束、证据审查、异常处置和最终验收。

### 2. 职责分工不等于解释权分离

仅仅为同一个模型分配多个角色，并不会自动产生独立审查。Aegis 更关心的是：一个角色能看到什么事实、能对什么作出判断、能否改变前序结论，以及它的结论由谁复核。

因此，Aegis 所说的“分离”不是角色扮演，而是对事实来源、解释范围和决定权的结构化约束。

### 3. 证据高于自我声明

“已经完成”“测试通过”“风险可接受”都只是陈述，不是工程事实。Aegis 要求重要状态由与之匹配的证据支持，并让证据本身接受独立判断。

在这一原则下，系统的推进依据不是模型的信心，而是工程事实是否足以支持下一步。

### 4. 失败必须关闭，而不是被叙述成成功

治理系统的价值不只在于顺利路径，更在于异常时是否会停止、保留事实并拒绝伪造闭环。任何无法证明的关键条件，都不应被自动解释为已经满足。

### 5. 项目需要拥有自己的认知

大多数工程仓库保存“做了什么”，却很少完整保存“为什么这样做”。Aegis 将设计动机、约束、取舍、反例、证据和失效条件视为项目资产，使后续工作能够继承判断基础，而不是反复从代码表面猜测历史意图。

### 6. 速度服从质量阈值

Aegis 的优先级是：事实正确、范围完整、证据闭合、结果可复现、长期可维护，最后才是速度。

当质量低于可接受阈值时，更快地产生结果并不构成正收益。Aegis 追求的是在可信边界内提高效率，而不是用速度替代可信度。

## 架构抽象模型

Aegis 可以被理解为五个相互约束的治理层，以及位于系统之外的最终责任主体。

```text
┌──────────────────────────────────────────────┐
│ 人类 / 组织 / 合同 / 法律：授权、边界与最终责任 │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│ 模型行为治理：识别失败模式并调整治理强度       │
├──────────────────────────────────────────────┤
│ 工程生命周期治理：约束工作如何进入、推进与结束 │
├──────────────────────────────────────────────┤
│ 职责与解释权分离：限制谁可以对什么作出判断     │
├──────────────────────────────────────────────┤
│ 项目语义空间：保存理由、约束、证据与失效条件   │
├──────────────────────────────────────────────┤
│ 运行时治理：把规则转化为可执行、可拒绝的边界   │
└──────────────────────────────────────────────┘
```

### 模型行为治理

这一层关注模型在真实工程活动中表现出的失败方式，而不是假设模型始终理性、稳定或一致。治理强度应由可观察的风险决定，并随着项目、任务和证据状况变化。

### 工程生命周期治理

这一层定义工程工作如何取得合法输入、如何形成边界、如何经过实现与验证、如何接受审查，以及在什么条件下才可以形成最终结论。

它提供的不是固定开发流程模板，而是一套“状态必须由事实推动”的工程秩序。

### 职责与解释权分离

这一层把生产事实、解释事实和批准事实视为不同权力。提出方案、实施方案、验证结果与接受结果在逻辑上相互制约，从而降低单一认知链条自我证明的风险。

### 项目语义空间

这一层承载项目长期认知。它让需求、设计、实现、验证和最终决策不再是互相孤立的文档或对话，而是具有来源、理由、证据和有效边界的连续语义。

### 运行时治理

这一层负责把软性规则变成工程系统真正能够执行的边界。它关心的不是规则写得是否漂亮，而是规则在推进、恢复、异常和绕过尝试中是否仍然成立。

### 外部责任主体

Aegis 不试图替代产品负责人、技术负责人、组织授权、合同约束或法律责任。系统可以保留判断链和证据链，但最终责任仍属于有权作出决定的人类与组织。

## 三个核心支柱

### 生命周期治理

生命周期治理负责回答：一项工作凭什么开始、凭什么继续、凭什么结束。

在 Aegis 的抽象中，工程活动会经历意图与约束形成、独立判断、受控执行、证据审查和最终验收。每个阶段都有自己的事实责任，后续阶段不能悄悄改写前序阶段已经确立的边界。

### 项目认知与推理库

推理库不是聊天记录，也不是普通知识库。它保存的是项目可继续依赖的判断结构，例如：

- 为什么采用当前方向；
- 哪些约束决定了这个方向；
- 哪些替代方案曾被否决；
- 什么证据支持当前结论；
- 出现什么变化后必须重新审查。

它的价值在于让项目能够回答“为什么”，并让未来的工程活动知道哪些历史结论仍然有效。项目由此获得一种超越单次会话的认知连续性。

### 运行时约束

仅有原则、提示词和文档不足以形成治理。运行时约束负责让关键边界不可被随意跳过，让推进、拒绝、恢复和失败都留下可验证事实。

它使 Aegis 从一套方法论变成可以实际约束工程行为的系统，但具体机制属于项目内部工程资产，不在本文公开。

## Aegis 形成的四个闭环

### 工程闭环

从意图到交付，结论必须经过相匹配的实现、验证、证据与验收，不能靠一次连续叙述直接跨越。

### 认知闭环

工程决策不仅产生结果，也更新项目对自身目标、边界、风险和历史理由的理解。

### 行为闭环

模型的工程表现会反过来影响后续治理方式，使治理基于观察到的行为，而不是固定不变的信任假设。

### 责任闭环

关键判断能够追溯到事实、证据、授权与最终接受者，使“谁基于什么批准了什么”成为可回答的问题。

## 人在 Aegis 中的位置

Aegis 不以消除人类工程师为目标。它希望重新分配人的注意力：

- 在前端聚焦目标、范围、约束和重大架构取舍；
- 在过程中处理真正需要责任判断的例外与冲突；
- 在末端检查关键证据并作出最终接受决定。

大量可制度化的中间治理工作由系统持续执行。人的注意力因此从重复追踪和上下文恢复，转向最需要经验、责任与价值判断的位置。

## Aegis 不是什么

Aegis 不是：

- 通用多模型编排框架；
- 通过多个角色提示词实现的“多智能体讨论”；
- LangGraph 或其他工作流技术的示例项目；
- 提示词、技能或最佳实践的集合；
- 普通代码生成器的外层包装；
- 用来替代工程判断的全自动审批器；
- 传统知识库、任务管理器或 CI 系统的简单组合。

这些能力可以成为系统的一部分或集成对象，但都不足以单独定义 Aegis。Aegis 的核心是工程治理、项目认知与可执行约束三者形成的统一系统。

## 当前范围

Aegis 当前专注于 Codex 参与的软件工程场景，优先研究单一受信任开发者在本地工程环境中，如何建立可验证、可恢复并能逐步增强的治理边界。

这一范围是当前工程阶段的主动收敛，不代表 Aegis 已经覆盖企业权限体系、多人协作治理、所有操作系统或所有模型生态。

## 当前进度

Aegis 已经历三个主要阶段：

### V1：原则探索

验证 AI 编程是否可以从“对话驱动”转向“工程状态与证据驱动”，并形成最初的职责分离、边界冻结和失败关闭原则。

### V2：真实工程验证

将治理思想放入复杂、长期、具有真实约束的软件工程任务中，验证它是否能够减少边界漂移、无证据完成和上下文丢失，并帮助人类维持对项目事实的控制。

这一阶段证明了方向具有工程价值，也暴露出仅靠流程约定和文本规则无法稳定落实治理的问题。

### V3：机制化建设（当前）

V3 的重点，是把经过验证的治理原则转化为持久的项目语义、独立的判断边界、运行时约束和可审查的证据链。

当前已经完成或正在稳定化的工作包括：

- 总体治理架构与核心抽象已经形成；
- 生命周期、项目认知和运行时约束已有可运行实现；
- 关键独立组件已经完成集成与隔离环境验证；
- 针对异常、恢复和边界绕过的验证正在持续加强；
- 面向真实长期项目的端到端工程闭环仍在推进。

### 成熟度声明

**Aegis 当前不宣称 Production Ready。**

项目正在按照生产级治理目标建设，但“按生产级标准设计”与“已经完成生产级验证”是两件不同的事。进入可公开交付的生产状态之前，仍需要完成更完整的真实环境验证、发布与安装闭环、长期运行观察、运维边界以及最终治理授权。

这一区分本身也是 Aegis 理念的一部分：系统不能用目标代替事实，也不能由实现者自行宣布尚未被充分证明的成熟度。

## 公开文档边界

本文档用于准确说明 Aegis 的问题定义、核心理念、架构抽象、适用范围和真实进度，不是实现教程或复刻指南。

为避免把项目的核心工程资产直接暴露为实现蓝图，本文有意不公开：

- 内部协议、状态转换和恢复细节；
- 治理规则的完整因果模型；
- 推理库的具体结构与演化算法；
- 运行参数、判定阈值和对抗样本；
- 权限、身份、见证与安全边界的具体构造；
- 私有组件之间的接口契约与部署方式。

这些内容决定了 Aegis 如何从理念变成可靠系统。理解 Aegis 不需要先获得这些细节，而复制 Aegis 的实现也不应只靠一份 README 完成。

## 项目定位

Aegis 试图建立的不是一个更聪明的编码助手，而是一种新的软件工程基础设施：

> 当 AI 成为主要生产参与者时，项目仍然拥有自己的边界、记忆、证据、判断秩序和最终责任。

这就是 Aegis 的核心。
