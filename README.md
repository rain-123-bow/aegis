# Aegis

> 面向 Codex 的 AI 原生软件工程治理与项目认知基础设施。

Aegis 是面向 OpenAI Codex 编码智能体的软件工程治理系统。Aegis 将需求边界、职责权限、工程证据、生命周期状态和项目决策转化为可持续执行的治理约束，使 Codex 参与的软件生产过程具备可审查、可追溯、可复现和可由人类问责的工程属性。

Aegis 使用“AI 原生软件工程”描述 AI 深度参与需求理解、方案设计、代码实现、验证和交付的生产方式。在这种生产方式中，Aegis 负责把资深工程师依靠经验维持的边界意识、审查习惯、证据要求和责任判断，转化为项目能够执行和继承的系统能力。

## 项目定义

**Aegis 治理 Codex 参与软件生产时的结论成立条件、判断权限、证据要求和认知沉淀过程。**

## 为什么需要 Aegis

成熟的软件工程会通过不同职责建立制衡：提出需求的人、设计系统的人、实现代码的人、验证结果的人和批准交付的人，通常不会拥有完全相同的视角与利益。

同一个 Codex 上下文可能连续承担以下工作：

- 解释目标；
- 选择方案；
- 编写实现；
- 设计验证；
- 解释验证结果；
- 宣布工作完成。

这种职责集中会让同一认知主体同时控制事实生产、事实解释和最终判断。各步骤可以保持局部一致，完整流程仍可能建立在错误前提上，并形成具有完整外观的错误结论。

Aegis 针对这种结构性风险提供四项治理能力：

1. **过程可信**：每个工程阶段按照明确的进入条件、完成条件和责任边界推进。
2. **判断独立**：关键结论由具有独立事实责任的判断环节复核。
3. **证据闭合**：工程状态由可检查的事实与证据推动。
4. **认知延续**：项目同时保存结果、成立理由、适用边界和失效条件。

## 核心理念

### 1. 治理对象是软件生产过程

Aegis 的治理对象覆盖从工程意图进入项目到工程结论获得接受的完整过程，包括边界形成、判断分离、执行约束、证据审查、异常处置和最终验收。

### 2. 职责分工包含解释权分离

Aegis 为每项职责定义可见事实、判断范围、变更权限和复核关系。角色名称只表示职责标签；事实来源、解释范围和决定权限共同构成有效的职责分离。

Aegis 使用“解释权分离”描述不同职责对事实进行解释和批准时受到的结构化限制。

### 3. 证据高于自我声明

“已经完成”“测试通过”“风险可接受”属于工程主张。Aegis 要求重要工程主张由相匹配的证据支持，并让证据接受独立判断。

系统在所需工程事实满足进入条件后推进到下一阶段。

### 4. 失败路径保持关闭

异常发生时，Aegis 停止受影响的推进路径、保留已知事实并维持未完成状态。缺少充分证明的关键条件保持为未满足状态。“失败关闭”表示异常路径无法继续产生完成结论，直至缺失条件经过重新验证。

### 5. 项目需要拥有自己的认知

Aegis 将设计动机、约束、取舍、反例、证据和失效条件作为项目资产保存。后续工程活动可以继承已有判断基础，并依据当前条件检查历史结论的有效性。

### 6. 速度服从质量阈值

Aegis 的优先级是：事实正确、范围完整、证据闭合、结果可复现、长期可维护，最后才是速度。

达到可接受质量阈值是效率收益成立的前提。Aegis 在可信边界内优化工程速度。

## 架构抽象模型

Aegis 的抽象架构由五个相互约束的治理层和外部责任主体构成。

```text
┌──────────────────────────────────────────────┐
│ 人类 / 组织 / 合同 / 法律：授权、边界与最终责任 │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│ 模型行为治理：识别失败模式并调整治理强度       │
├──────────────────────────────────────────────┤
│ 工程生命周期治理：约束工作如何进入、推进与结束 │
├──────────────────────────────────────────────┤
│ 职责与解释权分离：限制谁可以对什么作出判断     │
├──────────────────────────────────────────────┤
│ 项目语义空间：保存理由、约束、证据与失效条件   │
├──────────────────────────────────────────────┤
│ 运行时治理：把规则转化为可执行、可拒绝的边界   │
└──────────────────────────────────────────────┘
```

### 模型行为治理

模型行为治理层记录 Codex 在真实工程活动中表现出的失败模式，并根据可观察风险确定治理强度。治理强度是审查独立性、证据完整度和运行时限制严格程度的综合表达，随项目属性、任务风险和证据状态变化。

### 工程生命周期治理

工程生命周期治理层定义工作取得有效输入、形成边界、完成实现与验证、接受审查并形成最终结论的条件。

生命周期中的每次状态变化都需要相应工程事实支持。

### 职责与解释权分离

职责与解释权分离层将事实生产权、事实解释权和事实批准权分配给不同职责。方案提出、方案实施、结果验证与结果接受在逻辑上相互制约，从而降低单一认知链条自我证明的风险。

### 项目语义空间

项目语义空间承载项目长期认知，并将需求、设计、实现、验证和最终决策组织为具有来源、理由、证据和有效边界的连续语义。

### 运行时治理

运行时治理层将治理规则转化为工程系统能够执行的准入、拒绝、恢复和失败边界。规则在正常推进、异常恢复和绕过尝试中保持一致效力。

### 外部责任主体

产品负责人、技术负责人、组织授权体系、合同和法律共同构成 Aegis 的外部责任环境。Aegis 保存判断链与证据链；有权作出决定的人类和组织承担最终责任。

## 三个核心支柱

### 生命周期治理

生命周期治理负责回答：一项工作凭什么开始、凭什么继续、凭什么结束。

在 Aegis 的抽象中，工程活动依次经过意图与约束形成、独立判断、受控执行、证据审查和最终验收。每个阶段承担明确的事实责任。前序阶段已经确立的边界只能通过可追溯的重新审查进行变更。

### 项目认知与推理库

推理库是 Aegis 保存项目长期认知的持久化载体。推理库保存项目可以继续依赖的判断结构，包括：

- 为什么采用当前方向；
- 哪些约束决定了这个方向；
- 哪些替代方案曾被否决；
- 什么证据支持当前结论；
- 出现什么变化后必须重新审查。

推理库使项目能够回答工程决策“为什么成立”，并使未来的工程活动识别仍然有效的历史结论。Aegis 使用“项目认知”表示项目持久保存并持续校验这些判断基础的能力。

### 运行时约束

运行时约束将原则、职责和证据要求转化为系统可以执行的工程边界。关键边界受到强制检查，推进、拒绝、恢复和失败都会留下可验证事实。

运行时约束使 Aegis 具备实际约束工程行为的能力。运行机制属于项目内部工程资产，公开架构概览只描述其职责与作用。

## Aegis 形成的四个闭环

### 工程闭环

从意图到交付，每项结论依次取得相匹配的实现、验证、证据与验收结果。

### 认知闭环

工程决策产生工程结果，同时更新项目对自身目标、边界、风险和历史理由的理解。

### 行为闭环

模型的工程表现会影响后续治理强度，使治理规则持续响应已经观察到的行为与风险。

### 责任闭环

关键判断能够追溯到事实、证据、授权与最终接受者，使“谁基于什么批准了什么”成为可回答的问题。

## 人在 Aegis 中的位置

Aegis 将人类工程师的注意力集中到以下位置：

- 在前端聚焦目标、范围、约束和重大架构取舍；
- 在过程中处理真正需要责任判断的例外与冲突；
- 在末端检查关键证据并作出最终接受决定。

Aegis 持续执行可制度化的中间治理工作。人类工程师集中处理需要经验、责任与价值判断的事项。

## 系统范围

Aegis 当前面向以下工程环境：

- **智能体**：OpenAI Codex；
- **用户模型**：单一受信任开发者；
- **运行位置**：开发者控制的本地工程环境；
- **治理对象**：由 Codex 参与的需求理解、方案设计、代码实现、验证和交付活动；
- **核心能力**：工程生命周期治理、职责与解释权分离、项目认知沉淀、证据闭合和运行时约束。

企业身份与权限体系、多人协作治理、跨操作系统运行和其他模型生态属于后续扩展领域。当前范围使 V3 可以优先验证单用户本地环境中的治理完整性。

## 当前进度

Aegis 已经历三个主要阶段：

### V1：原则探索

V1 建立由工程状态与证据驱动 AI 编程活动的初步方法，并形成职责分离、边界冻结和失败关闭原则。

### V2：真实工程验证

V2 将治理原则应用于复杂、长期、具有真实约束的软件工程任务，验证其对边界漂移、无证据完成和上下文丢失的约束效果，以及人类对项目事实的控制能力。

V2 的验证结果确认了治理方向的工程价值，同时确认了流程约定和文本规则缺少稳定的执行强制力。

### V3：机制化建设（当前）

V3 的重点，是把经过验证的治理原则转化为持久的项目语义、独立的判断边界、运行时约束和可审查的证据链。

V3 当前状态：

- **已经形成**：总体治理架构与核心抽象；
- **已有可运行实现**：生命周期治理、项目认知和运行时约束；
- **已经验证**：关键独立组件、受控的端到端工程闭环和核心异常恢复路径；
- **正在验证**：长周期运行稳定性、边界绕过防护和生产运维约束；
- **尚待完成**：生产级发布与安装、长期项目验证、运维和最终治理授权闭环。

### 成熟度声明

**Aegis 当前尚未达到 Production Ready。**

项目采用生产级治理目标进行设计。生产就绪状态要求设计目标经过充分的真实环境验证，并形成稳定的发布、安装、长期运行、运维和治理授权闭环。

Aegis 仍需完成长期真实项目验证、生产级发布与安装、长期运行观察、运维边界以及最终治理授权。当前成熟度结论由已经完成的验证范围决定。

## 项目定位

Aegis 是面向 AI 生产参与者的软件工程治理基础设施：

> 当 AI 成为主要生产参与者时，项目仍然拥有自己的边界、记忆、证据、判断秩序和最终责任。

这就是 Aegis 的核心。
