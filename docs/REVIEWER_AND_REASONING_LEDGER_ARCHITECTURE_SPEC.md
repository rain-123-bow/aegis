# 审核者与推理库架构规格

状态：已确认，2026-08-20。

## 1. 目标

1. 审核行为与被审核物结论分离。
2. 审核者只产生审核意见，不修改任何上游产物。
3. 审核质量只由完整性、严谨性、证据绑定和问题分类评价，不由被审核物通过或拒绝评价。
4. 推理库以项目因果结构和客观现实条件为唯一内容，不承载运行状态。
5. 推理检索以可验证事实为权威，以语义索引为候选生成器。

## 2. 审核结果模型

审核节点必须分别输出以下字段：

```json
{
  "review_conclusion": "PASS | FAIL | UNDETERMINED",
  "finding_categories": [],
  "findings": [],
  "review_output_artifacts": []
}
```

字段语义：

- `review_conclusion`：被审核物是否满足约束，或现有材料是否不足以形成确定结论。
- `finding_categories`：问题的事实类别，例如测试方案缺陷、证据缺失、执行不完整、需求缺陷或实现方案缺陷。
- `findings`：问题、理由、证据索引和事实分类。
- `review_output_artifacts`：审核者自己创建的审核产物描述符。

机械约束：

1. 审核者不得输出接收者身份、节点名称、流程方向、继续、回退或终止指令。
2. `review_conclusion=PASS` 时不得存在阻断问题。
3. `review_conclusion=FAIL` 时必须至少包含一个有证据索引的问题类别。
4. 缺失必要输入或现有材料不能支持确定判断时，输出 `review_conclusion=UNDETERMINED` 并说明缺失项。
5. 审核工作是否完整执行，由协调器根据响应结构、输入覆盖、证据索引和角色契约机械判定，不由审核者自评。
6. 审核质量评价只检查输入覆盖率、论证完整性、证据真实性、证据索引完整性、问题分类准确性和结论一致性。
7. 审核者可以同时报告多类问题，但不得决定这些问题的处理顺序。

身份隔离：

1. 审核者只知道自己的职责、被审材料类型和输出契约。
2. 审核者不知道其他智能体、节点编号、注册表、流程拓扑和结论接收者。
3. 协调器不得在审核提示词、输入字段、输出字段或角色说明中泄露其他智能体身份。
4. 流程路由是协调器的私有机制，不属于审核语义。

## 3. 上游产物不可变规则

审核开始前，协调器向审核者提供冻结输入清单。每项包含稳定标识、绝对路径、字节数和 SHA-256。

审核者只能：

1. 读取冻结输入。
2. 在本角色专属输出目录创建审核报告。
3. 返回审核结论、理由和证据索引。

审核者禁止：

1. 修改、删除、重命名、移动、覆盖上游文件。
2. 改写上游 `README.md`。
3. 把审核意见写入需求、方案、测试方案、测试数据、测试报告或代码。
4. 生成内容被改变的“修正版”上游产物。
5. 通过修改共享索引改变上游产物的可见性或优先级。

协调器可以创建只读快照、描述符和交接索引，但不得改变上游内容。共享入口文件由协调器生成；任何审核者都没有共享入口文件的写权限。

## 4. 审核者职责

### 4.1 Master Reviewer（主控审核者）

输入：Master（主控智能体）编写的需求文档或实现方案文档，以及其冻结依据。

职责：

1. 审核完整性、无歧义性、内部一致性、可实现性和证据充分性。
2. 只输出意见和结论。
3. 不编写、不补写、不修订被审核文档。
4. 文档通过或拒绝不影响对审核工作的评价。

实例数量：一个或两个均支持。一个实例可连续审核需求与方案；两个实例可分别审核。两种模式使用同一输入输出契约。实例数量属于运行配置，不改变架构语义。

### 4.2 B（测试方案审核节点）

输入：A（测试方案编写节点）的测试方案、需求文档、实现方案和冻结推理上下文。

职责：

1. 审核测试方案是否完整覆盖需求、实现机制、失败路径、边界和证据要求。
2. 只生成测试方案审核报告。
3. 只输出通过、测试方案缺陷或材料不足等事实定性。
4. 不修改测试方案或其他上游产物。

### 4.3 D（证据审核节点）

输入：需求文档、实现方案、已批准测试方案、测试执行数据、执行回执、原始输出和冻结推理上下文。

职责：

1. 审核测试流程是否符合需求、实现方案和测试方案。
2. 审核测试方案是否被逐项执行。
3. 审核每项测试结论是否有真实、完整、可定位的数据支持。
4. 不修改任何输入文档、测试数据或执行产物。

问题分类：

- 测试方案本身存在缺陷：`TEST_PLAN_DEFECT`。
- 测试执行遗漏或未严格执行方案：`EXECUTION_INCOMPLETE`。
- 证据缺失、数据不足或结论无数据支持：`EVIDENCE_MISSING`。
- 需求文档自身存在缺陷：`REQUIREMENT_DEFECT`。
- 实现方案自身存在缺陷：`IMPLEMENTATION_PLAN_DEFECT`。
- 多类问题同时存在：完整报告全部类别，不选择处理对象或顺序。

### 4.4 F（终审节点）

输入：需求、实现方案、测试方案、全部测试证据、D（证据审核节点）报告、测试报告、代码、推理上下文、项目封印、远程见证和实际运行时身份。

职责：

1. 审核整个工程是否满足需求和架构合同。
2. 审核代码、测试过程、测试结论、推理依据和运行时证据。
3. 输出独立终审结论、原因和完整证据索引。
4. 不修改任何上游产物。

## 5. 协调器私有路由策略

本节只属于协调器实现，不得进入任何审核者的提示词、输入、输出或角色说明。

```text
测试方案审核通过 -> 测试执行阶段
测试方案存在缺陷 -> 测试方案重新编写阶段
证据审核通过 -> 测试报告阶段
证据审核发现测试方案缺陷 -> 测试方案重新编写阶段
证据审核发现执行不完整或证据缺失 -> 测试执行阶段
证据审核发现需求或实现方案缺陷 -> 主控处理阶段〔待确认〕
测试报告完成 -> 终审阶段
测试报告失败 -> 流程失败
终审完成 -> 流程结束
```

审核者只提供事实定性。协调器根据事实类别、当前权威状态和私有优先级表计算下一阶段。审核者不能观察或影响该映射。

节点执行失败与业务审核拒绝是两类状态。节点执行失败进入故障处理；业务审核拒绝由协调器私有策略处理。

## 6. 推理库第一性模型

### 6.1 权威层与索引层分离

权威层保存：

1. 客观观察。
2. 已验证事实。
3. 现实约束。
4. 需求。
5. 决策。
6. 规则。
7. 假设和待证结论。
8. 每项内容的原始证据描述符。
9. 项目内因果、支持、反驳、前提、依赖和替代关系。

索引层只用于定位权威记录。任何向量、全文索引或缓存都可删除并重建，不得成为事实真值。

### 6.2 技术栈

保留：

1. PostgreSQL（关系数据库）16 或更高且仍受上游支持的版本：权威记录、事务、约束、版本、递归关系查询、全文索引。
2. pgvector（向量检索扩展）0.8.0 或更高版本：语义候选生成。
3. Psycopg（Python 数据库驱动）3.3.4：事务和参数化查询接口；运行依赖保持精确锁定。
4. 项目文件证据：保存可独立重验的字节、大小和 SHA-256。

版本低于基线时迁移直接失败。不得关闭事务约束、证据校验或词法检索以兼容旧环境。

不引入独立图数据库。当前规模下，受约束关系表和递归查询已覆盖因果遍历。独立图数据库会增加双写、跨库事务、备份一致性和故障恢复边界，当前没有不可替代收益。

不把向量相似度作为事实依据。向量近邻只回答“可能相关”，不能回答“真实、有效、因果成立”。

### 6.3 最小权威实体

`statement`：稳定逻辑对象。

`statement_revision`：不可变内容版本，包含类型、文本、结构化条件、有效状态、适用范围、内容哈希和创建依据。

`evidence_descriptor`：证据路径、字节数、SHA-256、来源身份、采集时间和适用范围。

`relation`：从前提或原因指向结论或结果的有向关系。

`event`：追加式状态变化记录。

`current_projection`：从不可变版本和事件计算出的当前有效视图。

`embedding_profile`：向量提供方、模型、版本、维度、归一化方式和输入构造版本。

### 6.4 内容类型

```text
OBSERVATION  客观观察
FACT         已验证事实
CONSTRAINT   现实约束
REQUIREMENT  需求
DECISION     决策
RULE         规则
HYPOTHESIS   假设
CLAIM        待证或已证结论
```

### 6.5 关系类型

关系方向固定为“前提或原因 -> 结论或结果”。

```text
SUPPORTS     支持
REFUTES      反驳
ASSUMES      以前提依赖
SUPERSEDES   替代旧版本
CAUSES       导致
ENABLES      使能
PREVENTS     阻止
REQUIRES     必须依赖
```

每条关系必须包含：来源版本、目标版本、关系类型、适用条件、理由、证据索引、创建者和内容哈希。

边方向统一按“依据或先前状态 → 依赖项或后继状态”记录：`SUPPORTS`、`CAUSES`、`ENABLES`、`PREVENTS` 的来源直接作用于目标；`ASSUMES` 表示目标把来源当作前提；`REQUIRES` 表示目标必须依赖来源；`SUPERSEDES` 表示目标新版本替代来源旧版本。统一方向用于无歧义的上游因果遍历，不按英文动词的主谓顺序猜测端点。

### 6.6 事务不变量

1. 替代旧结论、新建新版本、创建替代关系和写入事件必须在同一事务完成。
2. 环检测与关系插入必须在同一串行化边界内完成，禁止并发插入绕过环约束。
3. 权威版本不可原地改写；修正只能创建新版本并使旧版本失效或被替代。
4. 删除索引不得删除权威内容。
5. 每个向量必须绑定完整 `embedding_profile`；模型变化后建立新索引代次。
6. 项目隔离条件必须进入主键、唯一约束和所有查询条件。

第一版向量输入模板固定为 `statement-v1`：由陈述类型、正文、结构化条件和作用域规范编码生成。向量写入时必须重算模板文本哈希并与调用方声明值一致；任意未知模板直接拒绝。向量值仍是可重建索引，不是权威事实。

环约束按关系语义执行：`SUPPORTS`、`ASSUMES`、`REQUIRES` 和 `SUPERSEDES` 构成证明或版本依赖，禁止闭环；`CAUSES`、`ENABLES`、`PREVENTS` 可以描述有状态系统的反馈回路，但遍历必须记录访问路径并受最大深度约束；`REFUTES` 表达冲突，不受无环约束。禁止把真实反馈系统强制改写为无环图。

### 6.7 检索流程

1. 解析项目、任务、时间、状态、类型和权限硬过滤条件。
2. 用全文检索查找精确术语、标识符、路径和规则。
3. 用向量检索生成语义候选。
4. 合并候选并保留命中来源和分数，不把分数解释成真值。
5. 从候选节点有界展开上游原因、必要条件、支持、反驳、假设和下游影响。
6. 按证据等级、有效状态、任务相关性、因果距离和冲突风险排序。
7. 生成包含冲突项、失效项、未证假设和证据描述符的冻结上下文包。
8. 对上下文包规范化编码并计算哈希；A-F（工程治理节点）运行期间只读取该冻结包。

上下文包使用 `aegis.reasoning_context_pack.v2`。包内必须包含词法和语义候选来源、因果展开关系、冲突关系、非活动版本、未证假设、全部引用证据描述符、检索参数和规范内容哈希。

权限边界适用于候选、因果展开、关系和证据描述符。任一因果闭包对象需要未授予权限时，整包拒绝生成；禁止静默删边后输出不完整因果链。

### 6.8 效率原则

1. 信息单位是可独立判断真假的陈述，不是任意长度文档切片。
2. 优先用项目、类型、状态和时间过滤缩小集合，再进行语义计算。
3. 数据量较小时使用精确向量查询；只有测量证明延迟不满足要求时才启用近似索引。
4. 近似索引启用后必须测量过滤条件下的召回率，并提供精确查询回退。
5. 上下文包只包含任务需要的因果闭包，不复制整个推理库。
6. 高频关系邻接和当前有效视图可以缓存，但缓存必须由权威事件代次校验。

## 7. `.aegis` 边界

`.aegis` 的唯一职责是保存推理库实例及其可重建索引、证据和上下文包。

禁止写入 `.aegis`：

1. 工作流运行状态。
2. 协调器租约。
3. 智能体会话状态。
4. 注册意图。
5. 临时运行日志。
6. 终审确认状态。

## 8. 实施顺序

1. 用户确认协调器对需求缺陷、实现方案缺陷和多类问题的私有处理策略。
2. 先写审核输出契约、角色所有权和禁止修改上游产物的失败测试。
3. 删除审核输出中的全部路由语义；由协调器机械判定审核执行状态，并将事实类别映射为私有流程动作。
4. 将共享入口写入权移交协调器；审核者改用角色专属报告。
5. 更新 Master Reviewer（主控审核者）、B（测试方案审核节点）、D（证据审核节点）、F（终审节点）的角色说明和机械校验。
6. 为推理库补充不可变版本、证据实体、因果关系、全文检索和向量配置身份。
7. 以事务测试验证替代原子性、并发环约束和项目隔离。
8. 以检索测试验证精确词法命中、语义候选、冲突暴露、因果展开和冻结上下文包。
9. 进行同模型独立对抗审核；按用户既定要求不进行跨模型审核。
10. 完成新的 Scope（运行时行为范围）审核、用户结构化确认、Seal（项目封印）和已授权的 protected remote witness（受保护远程见证）发布。

## 9. 验收条件

1. 审核者无法修改任何上游产物。
2. 被审核物拒绝时，完整严谨的审核仍被记录为审核工作完成。
3. 审核输出不包含任何其他角色、节点或流程方向；协调器对相同事实类别始终计算出相同流程动作。
4. F（终审节点）可以机械获得全部必审输入和证据索引。
5. 任意权威推理内容可追溯到不可变版本和原始证据。
6. 任意上下文包可重建其候选来源、因果展开过程、冲突项和哈希。
7. 向量索引删除或重建不改变权威事实和关系。
8. 并发写入不能产生部分替代、跨项目关系或非法关系环。

## 10. 已确认决策

1. 证据审核发现需求文档或实现方案自身缺陷时，协调器进入主控处理阶段。审核者只输出 `REQUIREMENT_DEFECT` 或 `IMPLEMENTATION_PLAN_DEFECT`，不知道处理对象。
2. 证据审核同时报告测试方案缺陷和执行缺陷时，协调器优先进入测试方案重新编写阶段；方案重新批准后再进入测试执行阶段。审核者只报告全部事实类别，不知道处理顺序。

## 11. 理论与机制依据

1. PostgreSQL（关系数据库）的递归公共表表达式支持层级和图式关系遍历：<https://www.postgresql.org/docs/current/queries-with.html>。
2. PostgreSQL（关系数据库）的全文检索以 `tsvector` 和 `tsquery` 表达词法文档与查询：<https://www.postgresql.org/docs/current/textsearch.html>。
3. PostgreSQL（关系数据库）的可串行化隔离用于检测无法串行成立的并发事务：<https://www.postgresql.org/docs/current/transaction-iso.html>。
4. pgvector（向量检索扩展）提供精确近邻、近似索引和与全文检索组合的混合检索；其近似索引过滤边界决定了过滤场景必须测量召回率并保留精确回退：<https://github.com/pgvector/pgvector>。
5. PostgreSQL（关系数据库）上游对主版本提供五年支持；本项目选择 16 作为长期维护基线，不接受已停止上游支持的数据库版本：<https://www.postgresql.org/support/versioning/>。
6. Psycopg（Python 数据库驱动）通过事务上下文和隔离级别控制数据库事务；串行化失败必须在新事务中重试：<https://www.psycopg.org/psycopg3/docs/api/connections.html>。
