## 1. 一句话介绍

我设计并实现了 Aegis。它是一套面向 OpenAI Codex 的 AI 原生软件工程治理系统，用结构化职责、冻结输入、独立审核、证据链和失败关闭机制，控制 AI 参与软件生产时的结论形成过程。

## 2. 面试开场版本

面试时，我会这样介绍这个项目：

> 我做的项目叫 Aegis，目标是解决 AI 深度参与软件开发后出现的工程可信度问题。Codex 可以连续完成需求理解、方案设计、编码、测试和结果解释，这种能力很强，同时也会让同一认知主体控制事实生产、事实解释和最终判断。只要早期前提出现偏差，后续步骤仍可能形成一条内部自洽、外部错误的完整链路。
>
> Aegis 把传统高级工程师和工程组织依赖经验维持的职责边界、审核制度、证据要求和异常处理，转化成可执行的运行时约束。系统会冻结需求、方案、代码和相关项目事实；让独立职责分别负责测试计划、计划审核、受控执行、证据审核、测试报告和最终审核；由协调器掌握流程状态和路由；每个关键结论都必须绑定可复核证据。
>
> 项目还维护一套推理库，用不可变版本、证据和因果关系保存项目长期认知。后续任务拿到的是经过筛选并冻结的因果上下文，而非依赖某次对话里没有持久化的背景信息。
>
> 当前 Aegis 已经完成核心治理链路、推理库、Windows 运行时控制和真实 Codex 控制面验收，也验证了关键崩溃恢复路径。项目仍在完成生产运维、长期稳定性、发布安装和最终治理授权闭环，所以我把它定义为已经具备可运行核心、仍处于生产化建设阶段的系统。

## 3. 我想解决的问题

我把问题归纳为五类。

### 3.1 认知链条过度集中

同一个 AI 上下文可以解释需求、选择方案、实现代码、设计测试并宣布完成。这里的风险来自权力集中：产出者同时掌握产出解释权和结果批准权。

### 3.2 自我一致性掩盖事实错误

模型擅长保持上下文内的一致性。错误前提一旦进入上下文，后续方案、代码、测试和报告可能围绕该前提持续自洽。最终文本看起来完整，结论与客观事实仍然可能分离。

### 3.3 工程主张缺少证据闭合

“已经完成”“测试通过”“可以交付”都属于工程主张。工程系统需要回答测试由谁执行、执行了什么、输入和运行时是否一致、原始输出在哪里、报告是否忠实引用证据。

### 3.4 异常恢复可能改变事实

进程崩溃、机器重启、会话丢失和中途修改文件都会破坏连续性。恢复逻辑如果直接接着旧状态运行，系统可能把失去证明的过程继续推进为成功。

### 3.5 项目知识被聊天上下文垄断

很多 AI 项目的设计理由、约束和历史选择只存在于某次对话中。线程结束或换人之后，项目留下代码，却失去了“为什么这样做”的可验证依据。

因此，我把 Aegis 的目标定义为：让项目拥有自己的边界、认知、证据、判断秩序和责任链。

## 4. 核心理念

### 4.1 项目边界由持久事实定义

需求、实现方案、运行范围、代码版本、项目封印和用户授权都要形成持久化记录。聊天内容可以帮助理解，不能覆盖这些高优先级事实。

### 4.2 事实生产权、解释权和批准权分离

负责产出的人或智能体，只对自己的产物负责。审核者负责判断产物是否满足条件，协调器负责根据事实类别计算流程动作。审核者看不到流程拓扑，也不能指定下一步交给谁。

### 4.3 证据高于声明

任何关键结论都要绑定原始输入、执行回执、输出文件、大小、哈希和来源身份。人类可读报告负责解释，机器可验证描述符负责证明。

### 4.4 关键路径采用失败关闭

证据缺失、身份不明、运行时变化、恢复连续性丢失或远端权威不可验证时，系统保持未完成或终止状态。系统只能在成立条件被重新证明后继续推进。

### 4.5 项目认知保存因果关系

项目需要保存事实和结论，也要保存结论依赖的前提、证据、反例、替代方案和失效条件。这样，历史决策才能被后续任务重新判断是否仍然有效。

### 4.6 人类承担最终责任

Aegis 可以保存判断链、执行门禁并暴露冲突。范围批准、风险接受和最终交付仍由具备责任的人类作出决定。

## 5. 总体架构

我把 Aegis 分为语义生产、独立判断、流程控制、项目认知、运行时证据和人类授权六个部分。

```text
                    人类用户 / 最终责任主体
                              │
                  确认需求、范围与启动授权
                              │
                ┌─────────────▼─────────────┐
                │ Master：长期语义执行者     │
                │ 需求、方案、代码、因果事实 │
                └─────────────┬─────────────┘
                              │ 独立审核与冻结
                ┌─────────────▼─────────────┐
                │ Runtime Coordinator        │
                │ 状态、身份、门禁、路由、恢复│
                └───────┬─────────┬─────────┘
                        │         │
             ┌──────────▼───┐  ┌──▼────────────────┐
             │ A-F 工程审核图 │  │ 推理库与冻结上下文 │
             └──────────┬───┘  └──┬────────────────┘
                        │         │
                ┌───────▼─────────▼─────────┐
                │ Seal、运行身份、执行证据、追踪│
                └───────────────────────────┘
```

### 5.1 Master

Master 是用户意图的长期语义执行者，直接负责需求、实现方案、代码和相应因果事实。它位于 A-F 审核图之外。

这项设计保证需求、方案和实现之间的语义连续性。独立智能体可以审核或取证，最终语义产物仍由 Master 直接形成，减少多层转述造成的意图损失。

### 5.2 独立审核者

独立审核者只读取冻结材料，只创建自己的审核报告。审核输出包含结论、事实类别、问题、理由和证据索引。审核者无法修改上游产物，也无法看到其他角色和流程方向。

### 5.3 Runtime Coordinator

协调器是运行时控制中心，负责：

- 工作流运行身份和唯一租约；
- 冻结输入、项目封印和运行范围校验；
- 角色线程、模型配置和技能绑定；
- 节点状态、尝试记录和恢复；
- 测试执行、资源限制和证据生成；
- 审核事实到流程动作的私有映射；
- 最终状态和交付资格计算。

协调器只执行机械策略。业务判断来源于冻结事实和独立审核结论。

### 5.4 A-F 工程审核图

| 阶段 | 职责 |
|---|---|
| A | 根据冻结需求、方案和推理上下文编写测试方案 |
| B | 独立审核测试方案的完整性和可执行性 |
| C | 把已批准测试方案转换成受控执行请求 |
| D | 审核执行是否完整、证据是否真实、结论是否闭合 |
| E | 根据已经审核的证据编写测试报告 |
| F | 对需求、方案、代码、测试、证据、推理依据和治理过程进行终审 |

### 5.5 推理库

推理库保存项目的长期因果认知，包括事实、约束、需求、决策、规则、假设、证据和关系。它负责为当前任务生成冻结上下文包，不承担工作流运行状态。

### 5.6 运行时证据组件

AegisSealCore 对批准的运行范围生成确定性项目封印，用于证明关键运行输入的版本边界。TraceRelay 记录受控进程会话与双向传输证据。Windows 进程控制负责限制执行资源、绑定进程身份并在协调器失效时终止受管进程树。

## 6. 关键处理逻辑

### 6.1 从用户意图到冻结工程输入

```text
用户目标
  → Master 编写需求
  → 独立审核
  → 用户确认并冻结需求
  → Master 编写实现方案
  → 独立审核需求与方案
  → 用户确认并冻结方案
  → Master 编码、记录因果事实并自测
  → 运行前检查
  → 用户授权启动 A-F
```

这个阶段的关键点是把自然语言意图逐步转化为可以计算哈希、检查版本和追溯责任的工程输入。需求或方案发生变化后，旧审核结论不会自动继承。

### 6.2 测试方案形成与审核

A 根据冻结需求、实现方案和推理上下文编写测试方案。B 对方案的需求覆盖、失败路径、执行方法和证据要求进行独立审核。

B 只输出事实结论和问题。协调器根据结论决定批准或创建新的测试方案轮次。旧版本和旧问题全部保留，修改问题编号或改写措辞不会被当作问题已解决；系统检查的是前提、推理、结论、证据缺口和替代解释是否发生实质变化。

### 6.3 受控测试执行

C 只能提交与已批准测试策略一致的执行请求。C 没有权力自行制造测试结果、退出码或执行回执。

协调器负责真正执行测试，并完成以下控制：

1. 核对工作目录、可执行文件、输入和完整环境；
2. 拒绝未绑定的 shell、内联代码和隐式宿主环境；
3. 在受资源限制、关闭即终止的进程容器中执行；
4. 保存实际进程身份、标准输出、标准错误和退出状态；
5. 生成 C 无法修改的执行回执和证据清单；
6. 执行前后重新校验全部冻结输入。

这套逻辑将“测试执行者说自己运行过”转换成“协调器可以证明实际运行过什么”。

### 6.4 证据审核与测试报告

D 同时读取需求、方案、已批准测试方案、执行回执、原始输出和证据清单，判断：

- 测试方案是否覆盖目标；
- 测试是否逐项执行；
- 原始证据是否完整；
- 报告结论能否由证据推出。

D 可以报告测试方案缺陷、执行不完整、证据缺失、需求缺陷和实现方案缺陷。它只描述事实类别。协调器在私有策略中决定回到测试方案、重新执行或交给 Master 处理。

D 通过后，E 根据已经审核的证据生成测试报告。E 失败时，流程无法进入终审。

### 6.5 最终审核与交付资格

F 接收经过机械冻结的最终审核输入清单，覆盖需求、方案、代码、测试方案、全部执行证据、测试报告、推理上下文、项目封印和治理过程。

F 必须给出结论、原因和完整证据索引。协调器逐项复核文件路径、大小、哈希和标识，并校验 F 的结构化结论与报告一致。

F 通过后，运行才能形成工程 PASS 和交付资格。F 拒绝时，Master 可以复核其结论结构和证据真实性，也可以记录分歧；Master 无权覆盖 F 的工程结论。最终材料提交用户决定。

### 6.6 运行中发生文件变化

A-F 运行期间，需求、方案、代码、运行范围、相关推理事实和项目封印保持冻结。协调器在节点边界重新计算摘要，同时使用 Windows 目录变化监控捕获“修改后还原”这类单纯比较最终哈希无法发现的行为。

检测到变化后，系统会：

1. 终止当前运行；
2. 保存变化路径、旧新摘要、时间和可用进程证据；
3. 标记工程结论失效；
4. 阻止同项目启动新运行；
5. 等待用户提交并封存变化原因。

记录原因只解除后续运行的启动阻塞。旧运行继续保留终止状态和原始结论。

### 6.7 进程崩溃和恢复

运行权威状态保存在项目目录之外，事务数据库保存权威状态，JSON 文件提供可读投影。协调器租约绑定运行 ID、实例 ID、进程 ID、进程创建时间和心跳，避免两个协调器同时接管同一项目。

协调器崩溃后，恢复逻辑先确认旧进程身份已经死亡。运行在冻结监听或受控进程阶段失去连续性时，旧运行被终止并标记连续性丢失；系统不会接纳一个无法证明身份的新进程继续旧运行。

需求和方案没有变化、规划阶段已经完整通过时，新运行可以复用批准的测试方案，从 C 重新开始。需求或方案发生变化时，新运行从 A 开始。所有旧运行和证据永久保留。

### 6.8 推理上下文生成

推理库检索采用以下顺序：

1. 按项目、类型、状态、时间和作用域执行硬过滤；
2. 用全文检索定位精确术语、文件、规则和标识符；
3. 用向量检索生成语义相关候选；
4. 合并候选，保留每个候选的命中来源；
5. 展开上游前提、原因、支持、反驳、假设和下游影响；
6. 暴露冲突、失效版本和未证假设；
7. 生成可重放、带证据描述符和内容摘要的冻结上下文包。

A-F 只能读取该冻结上下文包，不能在运行途中查询在线推理库。相关事实变化后，系统生成新上下文版本并启动新的审核运行。

## 7. 推理库的设计重点

### 7.1 权威事实与检索索引分离

PostgreSQL 保存不可变事实版本、关系、事件和当前投影，是权威层。全文索引和 pgvector 负责生成候选，是可重建索引层。

向量相似度只说明内容可能相关。一个结论是否成立，仍由事实状态、因果关系和证据决定。删除或重建向量索引不会改变项目事实。

### 7.2 最小信息单位是可判断真假的陈述

推理库围绕事实、约束、需求、决策、规则、假设和主张组织内容。每个版本都绑定证据和内容摘要。修正通过新版本、替代关系和事件完成，历史内容不会被原地覆盖。

### 7.3 因果图负责解释

关系可以表示支持、反驳、前提、替代、因果、使能、阻止和依赖。检索结果会展开相关因果链，使智能体同时看到结论、成立条件、反证和失效项。

### 7.4 为什么没有引入独立图数据库

当前项目规模下，PostgreSQL 的关系表、事务约束和递归查询已经覆盖因果遍历。增加图数据库会引入双写、跨库事务、备份一致性和恢复问题，收益不足以抵消复杂度。

## 9. 项目中最难的工程问题

### 9.1 让审核独立性成为系统属性

单独调用另一个模型实例不足以形成独立审核。提示词如果泄露流程方向，审核者仍可能为了“推动任务完成”调整结论。我的处理方式是让审核输出只包含事实类别和证据，把路由完全收回协调器。

### 9.2 让证据生产者失去解释结果的控制权

测试执行者只提交执行请求，协调器生成真实回执和证据清单，证据审核者再进行独立判断。这个边界避免测试执行者同时制造结果和解释结果。

### 9.3 在 Windows 上证明进程身份和死亡状态

PID 会复用，进程退出状态也可能与仍在运行的状态码产生歧义。Aegis 结合 PID、进程创建时间、可执行文件身份和内核等待状态判断所有权，并用 Job Object 约束整个进程树。

### 9.4 在崩溃后保持保守且可恢复

文件监控句柄和进程内状态无法跨协调器崩溃保存。我把“无法证明连续性”定义为终止条件，再允许新运行复用已经完整冻结的规划成果。这种策略牺牲部分恢复速度，换取结论可信度。

### 9.5 区分语义问题与文本变化

审核问题不能只按文本哈希或问题编号追踪。系统把问题建模为前提、推理、结论、缺失证据和替代解释，并要求审核者显式判断历史问题已经解决、仍未解决或被新问题替代。

## 10. 架构演进和取舍

### 10.1 Master 从工作流节点演进为长期语义执行者

早期设计把需求、方案和代码分散给多个智能体。实践中，多层转述增加语义损失，也让用户意图缺少稳定责任主体。现行架构由 Master 直接承担需求、方案和实现，独立智能体集中在审核与取证职责。

### 10.2 A-F 使用扁平职责图

扁平图让每个节点只承担一种事实责任。流程路由、状态恢复和身份校验集中在协调器，角色线程无法互相通信，也无法控制工作流。

### 10.3 选择 Codex 单模型边界

项目当前只承诺 Codex/GPT 的行为边界。这个范围允许我针对真实使用环境建立可验证契约，减少为了抽象兼容多个模型而引入的模糊行为。跨模型兼容属于后续扩展方向。

### 10.4 选择严格失败关闭

失败关闭会增加执行成本，也可能让一次长流程因为基础设施证据不足而重新开始。Aegis 的优先级把结论可信度放在速度之前，因此关键边界采用保守策略。

## 13. 常见面试追问

### 13.1 Aegis 和 CI/CD 有什么区别？

我的回答：CI/CD 主要自动化构建、测试和部署。Aegis 管理的是工程结论如何获得资格，包括需求和方案是否冻结、谁能判断什么、测试证据由谁产生、异常后是否还能继续、最终结论是否有完整责任链。CI/CD 可以成为 Aegis 的受控执行环境之一。

### 13.2 多智能体互相审核就能解决问题吗？

我的回答：实例数量只能提供一定视角差异。真正的独立性还需要输入隔离、职责隔离、上游不可写、流程拓扑隐藏、结构化结论和证据绑定。Aegis 把这些条件放进协调器和运行时契约。

### 13.3 推理库和普通 RAG 有什么区别？

我的回答：普通 RAG 关注找到相似文本。Aegis 推理库先保存不可变事实版本、证据和因果关系，再用全文和向量检索生成候选，最后展开因果链、冲突和失效条件。向量只是入口，事实权威来自数据库约束和证据。

### 13.4 审核者会不会也判断错误？

我的回答：会。Aegis 不假设某个模型永远正确。它限制单个错误能够造成的影响，保存审核使用的输入、推理、结论和证据，让后续审核和人类可以定位错误。系统追求可审查和可追责的判断过程。

### 13.5 为什么恢复时要终止旧运行？

我的回答：一旦文件监控、进程身份或执行证据连续性丢失，旧运行的成功条件已经无法证明。继续运行会把未知状态包装成成功。Aegis 保留旧运行，再用仍然有效的冻结成果创建新运行。

### 13.6 为什么先只支持 Codex？

我的回答：Aegis 当前就是针对 Codex 的真实工程系统。先把一个模型生态中的行为、线程、工具和运行时边界做深，可以得到可验收结果。多模型抽象可以在核心契约稳定后扩展。

### 13.7 这个项目最有技术含量的部分是什么？

我的回答：核心难点是跨越模型语义、工作流状态、操作系统进程、文件系统和数据库事务建立一条一致的权威链。每一层单独实现都不困难，真正困难的是让任何一层失去连续性时，系统都无法错误地产生成功结论。

### 13.8 当前为什么还没有宣布 Production Ready？

我的回答：关键功能通过验收只说明核心机制成立。生产就绪还需要长期运行数据、安装发布、数据库备份恢复、凭据管理、代码签名、范围批准和远程见证。我的成熟度结论严格受已经完成的证据范围约束。

## 14. 三分钟完整口述稿

> 我做的项目叫 Aegis，是一套面向 Codex 的 AI 原生软件工程治理系统。
>
> 我观察到一个核心问题：Codex 可以在同一个上下文里完成需求理解、方案设计、编码、测试和结果解释。这会让同一个认知主体同时控制事实生产、事实解释和最终判断。如果最初理解错了，后面的代码、测试和报告仍然可能围绕错误前提形成一条自洽链路。
>
> Aegis 的解决思路是把工程治理变成运行时可执行的系统。Master 负责连续理解用户意图并直接编写需求、方案和代码；独立审核者只审核冻结产物；A-F 六个职责分别负责测试方案、方案审核、受控执行请求、证据审核、测试报告和最终审核；Runtime Coordinator 管理状态、身份、冻结边界、流程路由和恢复。
>
> 在测试阶段，执行角色只能提交已经批准的执行请求，真正的命令由协调器在受限制的 Windows 进程环境中执行。退出码、输出和证据清单由协调器产生，再交给独立证据审核者判断。这样可以避免执行者同时制造结果并解释结果。
>
> 项目还有一套基于 PostgreSQL 和 pgvector 的推理库。PostgreSQL 保存不可变事实、证据和因果关系，向量只负责生成语义候选。系统会把与任务相关的因果链、冲突、失效版本和证据导出成冻结上下文，供后续审核使用。
>
> 对异常路径，我采用失败关闭策略。运行期间关键文件发生变化，或者协调器崩溃导致监控和进程身份连续性丢失，旧运行会被终止并保留证据。仍然有效的规划成果可以在新运行中复用，但未知状态不能继续推进成成功。
>
> 当前项目已经完成核心控制面、推理库、Windows 运行时、真实 Codex 端到端流程和关键崩溃恢复验收。本地测试基线共 291 项，三类真实验收都通过。后续工作集中在长期稳定性、生产数据库运维、签名发布、运行范围批准和远程见证，所以我目前把它定义为核心机制已验证、生产化仍在推进的项目。
