# Three-Store Linkage Policy

## 1. Purpose

Phase 23C defines the first Master-owned local demo linkage validation across Archive, Knowledge, and Causal stores.

It answers:

```text
Can the local demo Archive / Knowledge / Causal stores reference each other without broken IDs, store-type confusion, or truth-boundary leakage?
```

Phase 23C is not production store infrastructure.

It does not implement:

- production Archive / Knowledge / Causal backend
- production encryption
- key lifecycle
- remote sync
- canonical or global causal merge
- new department topology
- long-lived linkage agent profile
- ordinary-agent direct store writes
- mutation of Archive, Knowledge, or Causal store state

## 2. Linkage boundary

Phase 23C validates cross-store references after the three local demo persistence boundaries exist:

```text
Archive   = what happened
Knowledge = what is known
Causal    = why a judgment holds
```

The linkage validator is a Master governance tool, not a fourth truth layer.

It may validate:

- Archive events promoting assets into Knowledge or Causal candidates / entries / facts;
- Knowledge entries citing Archive events or external source material as evidence;
- Causal facts citing Knowledge entries, Archive events, Causal facts, or source review decisions;
- explicit Master-verified expected links.

It must not infer new truth from the existence of a link.

## 3. Accepted local store roots

Phase 23C reads local demo roots generated by prior phases:

```text
archive/
knowledge/
causal/
```

The validator accepts JSON-formatted YAML-compatible `.yaml` payloads, consistent with Phase 22C / 23A / 23B local demo serialization.

## 4. Valid local typed references

The validator recognizes these local typed references:

```text
archive:E0001
archive/active/segment_0001/events/E0001.yaml
knowledge:K0001
knowledge/entries/K0001.yaml
causal:F0001
causal/facts/F0001.yaml
```

Short IDs are also accepted when the target store is determined by the ID prefix:

```text
E0001 -> Archive event
K0001 -> Knowledge entry
F0001 -> Causal fact
```

External source references, such as test reports or source files, are allowed but are not treated as local typed references.

## 5. Required validation rules

Phase 23C must reject when:

- a typed local reference points to a missing Archive event, Knowledge entry, or Causal fact;
- a field expects Knowledge but receives a Causal ID, or expects Causal but receives a Knowledge ID;
- `promoted_assets` targets Archive instead of Knowledge or Causal;
- Knowledge `evidence_refs` use local Knowledge or Causal references instead of Archive or external source material;
- Archive payloads claim truth production;
- Knowledge payloads claim Causal truth production;
- Causal payloads claim global causal truth merge or production persistence;
- duplicate local store IDs are detected;
- an optional linkage request is not Master verified;
- an optional linkage request attempts production writes or global truth mutation.

## 6. Archive linkage rules

Archive may contain references such as:

```yaml
promoted_to_knowledge:
  - K0001
promoted_to_causal:
  - F0001
promoted_assets:
  - target_store: knowledge
    target_id: K0001
  - target_store: causal
    target_id: F0001
```

These links mean an Archive event produced material that was promoted or staged elsewhere.

`promoted_assets` may target only `knowledge` or `causal`. `archive -> archive` promotion is invalid because Archive records events and does not promote events into Archive truth or Archive-derived truth.

They do not mean Archive produces truth.

## 7. Knowledge linkage rules

Knowledge entries may cite Archive events or external source material through `evidence_refs`. Local Knowledge or Causal records must not be used as Knowledge evidence.

Example:

```yaml
evidence_refs:
  - archive:E0001
  - runtime_test_reports/PHASE_23C_THREE_STORE_LINKAGE_ACCEPTANCE_REPORT.md
```

Knowledge still records only verified neutral facts, constraints, interfaces, environment facts, policy facts, version facts, and glossary facts.

Knowledge `evidence_refs` may contain:

- `archive:E0001` typed local Archive refs;
- external source refs such as reports, source files, logs, or artifacts.

Knowledge `evidence_refs` must reject:

- `causal:F0001`;
- `knowledge:K0001`;
- short local IDs inferred as Causal or Knowledge IDs.

Knowledge does not produce Causal truth and must not inherit Causal facts as evidence for static knowledge.

## 8. Causal linkage rules

Causal facts may cite local Archive / Knowledge / Causal references as evidence or dependencies.

Example:

```yaml
evidence:
  - archive:E0001
  - knowledge:K0001
depends_on:
  - F0001
```

Causal facts still require prior Causal admission and Master causal review before persistence.

Phase 23C validates references. It does not perform canonical/global causal merge.

## 9. Optional Master linkage request

A Master-verified linkage request may ask the validator to check explicit expected links:

```yaml
request_type: three_store_linkage_request
request_id: TSL-001
master_verified: true
expected_links:
  - from_store: archive
    from_id: E0001
    to_store: knowledge
    to_id: K0001
    link_type: promoted_asset
```

If present, the request is itself an admission object and must be Master verified.

## 10. Summary

```text
Phase 23C validates cross-store reference integrity.
It does not write Archive, Knowledge, or Causal stores.
It does not create truth.
It does not merge global causal state.
It does not add a new department or long-lived agent.
```
